The .folio layout

A .folio is a zip with a fixed layout, and nothing inside it points outward. Archives of community work tend to die the same way, by depending on something stored somewhere else, so a game carries everything it needs. 

my-game.folio
├── manifest.json            required
├── walkthrough.folioscript  required: the proof it can be finished
├── brief.json               optional: what you were aiming for
├── logic/
│   ├── game.z3              a Z-machine story, or
│   └── world.json           a declarative world
├── presentation/
│   ├── roommap.json         Path A only, required
│   ├── scenes.js            optional: the pictures
│   └── verbmap.js           optional on Path B, needed on Path A
└── checksums.json           written on pack, verified on load

Checksums are SHA-256 per entry, written by folio pack and verified every time a game is loaded. A mismatch or a missing entry refuses to load rather than playing a game that is not the one that was checked.

Every presentation/*.js is evaluated when the game boots. On Path B nothing else in the container can contain code, which is what makes a world from a stranger safe to open. A Path A game contains a compiled program by definition.

manifest.json

Seven fields are mandatory. Anything missing is E100.

id
string · required A short slug, unique to your game.
title
string · required Shown in the gallery and the player.
author
string · required You.
folioVersion
string · required The format version, semver. "0.1.0" today.
logicType
string · required "world" or "zmachine".
license
string · required An SPDX identifier, or "unknown". Unknown is playable but not hostable, and warns with W105. The interactive fiction archive omitted a licence field from its metadata standard and its curators have been unable to tell mechanically what they may serve ever since, which is why this is mandatory here.
contentRating
string · required One of all-ages, teen, mature.
capabilities
string[] Engine features the game needs. Anything not on the known list is E220, because a game asking for an engine we are not should be refused rather than glitched. Known: darkness, timed-events, combat, containers, npc-dialogue, multi-save, custom-verbs, sound, score.
aiDisclosure
object What was generated and what a human reviewed. Omitting it warns with W106. State it precisely: a claim that outruns the pipeline is the failure that costs trust. { "prose": "none", "art": "none", "note": "…" }

walkthrough.folioscript

One command per line. # begins a comment and runs to end of line. Blank lines are ignored. The file is the proof the game can be finished, so it is run from a cold start with nothing injected. 

# Cellar Door — cold start, no state injection
north
take key
expect: room HALL
south
unlock cellar-door
expect: score 5
expect: room ID
Assert the player is in that room.
expect: score N
Assert the score right now.
expect: moves N
Assert the move count.
Line numbers count commands

A failure reports as line 2 meaning the second command, not the second line of the file. Comments and blanks are stripped before numbering, so an assertion on file line 5 can be reported as line 2.

The command line

CommandDoes
folio pack <dir> <out.folio>Assemble a directory into a game, writing checksums
folio validate <file>Run the tiers and print what the game may claim. Exits non-zero on error
folio play <file>Play in the terminal. Both logic paths, same loop
folio info <file>Manifest summary and every entry with its size
folio profile <file>Replay the walkthrough and measure the design shape
folio brief [brief.json]Resolve authoring dials into concrete targets and thresholds
folio calibrate <story.z3>Derive a Path A room map from a story file. -o writes it

Certification

Games are checked in tiers, and a badge claims only what was actually verified.

TierProves
T0 schemaThe manifest is complete and well-formed
T1 integrityReferences resolve, assets decode, capabilities are supported
T2 graphNo dead ends exist, computed from the world rather than asserted
T3 replayOne path completes, from the beginning, with no state injection
T4 designChain depth, item economy, map shape and pacing

T2 and T3 check different things and neither implies the other. T3 starts every run from the game's own opening state, because a test that can teleport the player or hand them an item only shows that a scene works from a position nobody could reach. Inform's TEST ME has allowed exactly those stipulations for twenty years, and it is the reason a green run there proves less than it looks like.

BadgeMeans
invalidAt least one error. It will not be hosted
validT0 and T1 passed. Where every Path A game rests today
playableT3 passed: a path to the ending exists
certifiedT4 passed with no design warnings. Deliberately hard
Playable means a path exists

It does not mean a human can find it. Those are separate claims and the badge keeps them separate. The check that speaks to findability is a blind solver, which is designed and not built.

The dials

Difficulty is not one quantity. It is how deep puzzle chains run, how plainly clues are stated, how far a key sits from its lock, and how long a game dares to go without paying out. You state an intent and the brief resolves it into numbers.

The resolved brief is both the generation target and the validation threshold. Ship it as brief.json and T4 grades your game against your own intent rather than against generic defaults, which is what stops a difficulty setting quietly becoming decorative.

DialValuesEffect
lengthshort · standard · epic12, 35 or 82 rooms. Or {"rooms": n}, or inferred from your source
difficultygentle · standard · cruelChain depth 3 / 5 / 9, gate distance 1 / 3 / 6, dry spell 20 / 45 / 69
deadlinessnone · fair · classic0, 3 or 8 deaths. Fair warns you first, classic does not
sprawllinear · balanced · open0.05, 0.35 or 0.67 map loops per room
densitysparse · balanced · packed25%, 43% or 70% of objects are takeable
folio brief brief.json

Resolved brief
  A 12-room game with puzzle chains up to 3 steps deep.
  forgiving — clues near their locks, frequent rewards.
  nothing can kill you.
  Map: some circling back.
  World: mostly scenery, a few things that matter.

"Standard" is measured rather than guessed. It is Zork I, replayed and recorded: 82 rooms, 0.67 loops per room, a 43% take rate, a reward about every 11.5 moves, and one stretch of 69 moves with no reward at all.

Two of those numbers changed how the checks work. Most of Zork's world is scenery by design, so a world where everything is useful reads as a list of tasks rather than a place. And one loop in a fifty-room map is still a corridor, so map shape is measured per room rather than in total.

Chain depth is capped by what the map can carry. A twelve-room world cannot host a nine-step chain without every room being a gate, so a small "cruel" game is honestly reported as capped rather than silently graded against something impossible.

Embedding a game

The player is a single file with no dependencies. Host a .folio anywhere and point at it.

<iframe src="https://folio.games/play/?game=https://example.com/my-game.folio"
        width="720" height="680" style="border:0"></iframe>

You can also download the player and serve both yourself. A game of Folio has no server-side component and runs entirely in the browser, so it keeps working on a static host, behind a firewall, and offline.

Games are small. The worked example in this repository is 2.4KB packed, and a full Z-machine game with art runs to a couple of hundred kilobytes.
