How Folio works

An engine, a file format, and a way of proving a game can be finished. This is the reference manual. It is more detailed than the README on GitHub, and where the two disagree, this is the one that is right.

The pieces

Folio is four things that fit together, and it is worth knowing which one you are working with at any moment.

the engine
Reads a game and draws it. It runs in a browser with no build step and no server. The interface it draws is fixed: a scene, a verb grid, a compass, a text pane, an inventory strip, a status bar. You do not lay that out.
the .folio
One zip file holding a whole game, with nothing pointing outside it. This is the unit of creation, sharing, validation and play. See the layout reference.
the validator
Five tiers of checks that decide what a game may claim. The interesting one replays the game's own walkthrough from a cold start and requires it to reach the ending. See certification.
the CLI
folio pack, validate, play, info, profile, brief and calibrate. Everything the site does, the command line does too.

Two logic paths

A game's logic comes from one of two places, and which one you have determines most of what you will do. The manifest declares it as logicType.

Path A · zmachinePath B · world
You start with An existing Z-machine story file, v3, v5 or v8 Nothing. A story, an idea, a novel
Logic lives in The original binary, run unmodified logic/world.json, plain data
You supply A room map, mostly derived by folio calibrate The whole world: rooms, items, rules
Can contain code Yes, it is a compiled program No, and it never can
Validator reaches T0 and T1 only T0 through T4
Guide Porting a game Writing a world

Both paths hand the engine the same object, the World State Contract, and the engine never learns which one it got. That is what lets one renderer draw a 1988 binary and a world compiled from a novel last week. The contract is specified in packages/format/world-state-contract.md and summarised in Scenes and verbs, because it is the object your scene code reads.

The authoring loop

Whichever path you are on, the working loop is the same four commands. There is no project file and no scaffolding step. A game is a directory. 

# 1. assemble the directory into one file
folio pack my-game/ my-game.folio

# 2. find out whether it holds together, and what it may claim
folio validate my-game.folio

# 3. play it in the terminal, which is the fastest way to feel a problem
folio play my-game.folio

# 4. measure its design shape against the corpus
folio profile my-game.folio

Most of your time goes into step two. The validator is deliberately talkative and its warnings are the closest thing Folio has to a design review. Every code it can emit is documented in the finding codes reference, with what causes it and what to do about it.

What exists today

Folio is an early project and some of what has been designed is not built. Reading this manual should not leave you guessing which is which, so here is the line.

Built and working

  • The engine, both logic backends, and the browser player
  • The .folio container, with checksums verified on load
  • The validator, tiers T0 through T4, and the corpus profiler
  • The folio command line, all seven commands
  • Room-map calibration, which derives a Path A binding from a story file and reports the parts it could not finish rather than guessing them
  • The authoring dials, which resolve intent into targets and thresholds

Designed, not built

The map editor is real, and it is a first slice

folio.games/editor draws a world: rooms on a canvas, exits you draw between them, regions in colour, and the real validator running on every edit. The direction of an exit comes from where the rooms sit, so the map cannot claim two places are adjacent while showing them apart.

It edits rooms, exits, regions, and what is in each room, and it previews the room's picture using the same backdrops folio scenes writes out.

Puzzles are placed rather than written. A locked way is not one rule: it is a flag, a condition on the exit, the rule that satisfies it, and the rule that answers when you try without the key. Choosing "locked way" writes all four, in the order that keeps them reachable, which is the part that is easy to get wrong by hand. The same goes for a reward, an ending and something fatal.

Prose, timers and anything outside those shapes still want the format itself, which is what the rest of this manual is for.

  • The Story Compiler. Turning a novel or screenplay into a world automatically. The pieces it needs exist around it, the compiler itself does not.
  • The art pipeline. Nothing generates scene art. A Path B game currently renders every room as a placeholder unless you write the drawing code yourself. See Scenes and verbs.
  • The blind solver. T4 measures design shape but cannot yet tell you whether a human could find the solution.
  • The gallery backend. Uploads, accounts and moderation.

Using Folio from another tool

Nothing needs to connect to us. The format is JSON with a closed vocabulary and the checker is a command, which is all another program or another model needs to produce a working game.

the schema
world-0.1.0.json, served with permissive CORS. Editor autocomplete, constrained generation, and validation from any language. The validator checks against this same file.
the compact spec
folio.games/llms.txt is the whole authoring format in one file, written to be read by a model in a single fetch rather than by a person across seven pages. It carries the vocabularies, a complete worked example, and the failures worth expecting.
the checker
npm i -g folio-engine, then folio validate. Exits non-zero on error and names the exact path of the problem, which is what makes a generate-and-check loop possible.

A world is data and cannot contain executable code, so validating or playing one from a stranger is safe. A Path A game contains a compiled program by definition, and anything running games automatically should treat the two differently.

The MCP server

None of the above needs a connection. What a connection buys is the loop: write a world, check it, read the exact failure, fix it, without a person moving files between a chat window and a terminal. folio-mcp is a stdio MCP server exposing ten tools, and it has no dependencies of its own. 

// claude_desktop_config.json, or any MCP client
{
  "mcpServers": {
    "folio": { "command": "folio-mcp" }
  }
}
ToolDoes
folio_nextWhat to do next, read off whatever exists so far
folio_specThe whole authoring format in one call
folio_schemaThe JSON Schema, for constrained generation
folio_validateCheck a world inline. Works on a draft with no walkthrough yet
folio_play_startBoot a world and get the opening text
folio_play_sendSend one command, get the response and state
folio_play_endDiscard a session
folio_briefResolve the dials into targets
folio_packAssemble the finished game and return the file
folio_calibrateDerive a Path A room map from a story file

folio_next is the part that makes this a process rather than a pile of tools. It reads whatever exists and returns the ordered remaining work with a reason for each, so an agent can start from nothing, from a half-written world, or from a week-old draft and get the same answer. It is deliberately not a wizard: the agent asking the questions is better at that than a script could be, and a wizard breaks the moment somebody arrives holding something half-finished.

The order it enforces has one load-bearing rule. Structure before prose: rooms, exits, rules and the walkthrough first, with every description left empty, and only then the writing. That is what stops a long source compiling into six rooms and a walk, because a bad map is thrown away while it still costs nothing rather than after forty descriptions are written.

The play tools are the interesting pair. Point an agent at a game with the walkthrough withheld and you have a blind solver, which is the check Folio cannot currently make: a badge can say a path exists and cannot say a person would find it. Anything that runs is Path B only, for the reason above.

Where to go next

If you have never built one, start with Your first game. It builds a small complete game from an empty directory and takes about ten minutes.

If you have a story and want to build a game out of it, Writing a world is the full reference for the format you will be writing.

If you have a Z-machine game you want to give pictures to, read Porting a game first. It is honest about a missing piece in that workflow, and you should know about it before you start.
