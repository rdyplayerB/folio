How Folio works

An engine, a file format, and a way of proving a game can be finished. The full reference lives with the source; this is the shape of it.

Getting started

npm i -g folio-engine

folio pack my-game/ my-game.folio    # assemble
folio validate my-game.folio         # check it
folio play my-game.folio             # play in the terminal
folio profile my-game.folio          # measure its design shape

A game directory needs a manifest.json, a walkthrough.folioscript, and either a Z-machine story file or a world.json. Everything else is presentation.

The .folio format

A .folio is a zip with a fixed layout, and it carries everything the game needs. Archives of community work tend to lose their contents the same way, by depending on something stored elsewhere, so nothing here points outward. 

my-game.folio
├── manifest.json            id, title, author, licence, rating
├── walkthrough.folioscript  required: the proof it can be finished
├── logic/
│   ├── game.z3              a Z-machine story, or
│   └── world.json           a declarative world
├── presentation/            scenes, sprites, verb map, bindings
└── checksums.json           written on pack, verified on load

Three manifest fields are mandatory: licence, where unknown means playable but not hostable, content rating, and a structured AI disclosure.

The World State Contract

The renderer reads one thing, a plain object describing the world right now. It never learns which kind of game produced it, which is how the same code draws a 1988 binary and a world compiled from a novel last week. 

{
  roomId:    "LIVING-ROOM",
  score: 35, moves: 13, dark: false,
  objects:   ["LAMP","SWORD","RUG"],
  inventory: ["LAMP"],
  exits:     { NORTH:"KITCHEN", EAST:false },
  flags:     { LAMP:{ ONBIT:true } }
}

exits has three states rather than two. A room id means you can go, false means the way exists but is blocked, and absent means there is no way at all. The middle state is what lets the compass grey out a door you can see and cannot yet open.

Certification

Games are checked in tiers, and a badge claims only what was verified.

TierProves
T0 schemaThe manifest is complete and well-formed
T1 integrityReferences resolve, assets decode, capabilities are supported
T2 graphNo dead ends exist, computed from the world rather than asserted
T3 replayOne path completes, from the beginning, with no state injection
T4 designChain depth, item economy, map shape and pacing

T2 and T3 check different things and neither implies the other. T3 starts every run from the game's own opening state, because a test that can teleport the player or hand them an item shows that a scene works from a position nobody could reach.

Playable means a path exists. It does not mean a human can find it. Those are separate claims and the badge keeps them separate.

The dials

Thresholds come from replaying Zork I and measuring what it does: 82 rooms, 0.67 loops per room, a 43% take rate, a reward about every 11.5 moves, and one stretch of 69 moves with no reward at all.

Two of those numbers changed how the checks work. Most of Zork's world is scenery by design, so a world where everything is useful reads as a list of tasks rather than a place. And one loop in a fifty-room map is still a corridor, so map shape is measured per room.

Scale is the one thing that does not come from the corpus. Zork has 82 rooms because Zork is Zork, so a game adapted from a short story is measured against its own source or the brief you set.

Embedding a game

The player is a single file with no dependencies. Host a .folio anywhere and point at it: 

<iframe src="https://folio.games/play/?game=https://example.com/my-game.folio"
        width="720" height="680" style="border:0"></iframe>

You can also download the player and serve both yourself. A game of Folio has no server-side component and runs entirely in the browser, so it keeps working on a static host and offline.
