Making games

Porting a game

Path A takes a Z-machine story file that already exists and gives it the pictures and the verb grid it never had. The original binary runs unmodified and stays the referee. Read the section on the room map before you commit to a game, because that is where the work actually is.

What porting means here

Folio does not reimplement your game, translate it, or paraphrase it. It boots the actual story file in a Z-machine interpreter and reads the interpreter's live memory to work out what to draw. Every parser refusal, every combat roll and every piece of prose is the original's.

The engine only ever reads. It never writes to interpreter memory, which is what makes the claim honest: the game underneath is the one people played, and the pictures are a layer on top of it.

What you supply

A Path A game directory looks like this. The manifest declares "logicType": "zmachine".

my-port/
├── manifest.json
├── walkthrough.folioscript
├── logic/
│   └── game.z3               the story file, unmodified
└── presentation/
    ├── roommap.json          required: binds the binary to stable ids
    ├── verbmap.js            optional: what the buttons send
    └── scenes.js             optional: the pictures

The story file's extension must match its header. A file named .z3 whose header says version 5 is rejected with E202, because shipping the wrong story is a mistake that otherwise surfaces in front of a player.

Versions 3, 5 and 8 are accepted by the validator. The interpreter is a v3 implementation, so a v5 or v8 story will pass validation and may still fail to run. Treat v3 as the supported case today.

verbmap.js and scenes.js are covered in Scenes and verbs. They are optional in the sense that the game boots without them and unplayable in the sense that a Z-machine game needs a verb map to turn a click into a command its parser understands.

The room map

A Z-machine binary does not know it has rooms called anything. It has numbered objects. The room map is the table that says object 27 is the kitchen, and without it the engine cannot tell which scene to draw.

It is game data, not engine data, so it ships inside the .folio at presentation/roommap.json rather than living with the engine.

ROOMMAP
object · checked Z-object number to a stable room id. { "27": "KITCHEN", "33": "CELLAR" }
OBJMAP
object · checked Z-object number to a stable object id, for everything that is not a room.
ATTR
object · checked ZIL flag name to attribute bit number. { "TAKEBIT": 17, "OPENBIT": 11, "ONBIT": 19 }
ADVENTURER
number The z-object number of the player object. Needed to work out what is being carried rather than what is lying about.
DIRPROP
object Direction name to the property number that holds that exit. { "NORTH": 31, "SOUTH": 28 }
EXIT_HAS_ROOM
number[] Which exit property lengths begin with a destination room number, as opposed to a refusal message or a routine. For Zork I this is [1, 4, 5].

The validator checks that ROOMMAP, OBJMAP and ATTR are present, and E205 names whichever is missing. The other three are not checked and their absence shows up as a game that draws the wrong room or reports an empty inventory.

Building it: folio calibrate

You do not write a room map by hand. folio calibrate reads the story file and derives one, then tells you exactly which parts it could not finish. 

folio calibrate logic/game.z3 -o presentation/roommap.json
game.z3  v3 release 119 serial 880429, 250 objects

  rooms           110   from the containment tree
  objects         137   3 unnamed internals skipped
  directions       13   61% of exits lead back, which is what named them
  player           44   the unplaced actor

  attribute bits
    ✓ DOORBIT     22   every object named as the door of a DEXIT exit carries it
    ✓ ACTORBIT    30   the one actor the game never placed, and its name says who it is
    ? TAKEBIT      —   no reliable static signal; confirm from the census
    …

Everything structural comes out exact. Checked against Zork I, whose correct map is known independently, calibration recovers all 110 rooms and nothing else, names all 13 direction properties correctly, and finds the player object. It is deterministic, so re-running it never shuffles the map out from under your scene art.

Why the room ids are minted rather than discovered

This looks like it should be impossible, because short names are not unique. Zork I has fifteen objects called "Maze", five called "Dead End", five stretches of "Frigid River" and four patches of "Forest". Decoding names leaves you with dozens of indistinguishable candidates.

It is only impossible if the ids already exist and have to be matched. When nobody has named anything yet, the ids are yours to mint, so the fifteen maze rooms become MAZE-1 through MAZE-15 and it does not matter which physical room got which number. The numbering is stable for a given binary, which is the property that actually matters.

Rooms are found through the containment tree rather than by guessing from exit shape. ZIL declares every room inside one pseudo-object, and its children are the map exactly. Directions are named by reciprocity: under a correct assignment, walking north and then south brings you back most of the time, and under a wrong one it almost never does.

The eight flags you finish by hand

About two minutes of work

Attribute bit numbers are assigned per game by the compiler, and nothing in a compiled object table says which bit means "the player may pick this up". Two flags leave a clean trace and are derived. The other eight are reported as a census instead of guessed, because a wrong TAKEBIT means the engine believes nothing in the game can be picked up, and that is not a thing to discover from a player.

The census lists every attribute bit with the names of the objects carrying it, which makes the answers obvious on sight: 

    bit 17  n=60   jade figurine, torch, lunch, matchbook, crystal trident
    bit 18  n=20   altar, pedestal, brown sack, jewel-encrusted egg, basket
    bit 19  n=36   Temple, Up a Tree, torch, Land of the Dead, Rocky Ledge
    bit 12  n=5    wooden door, basket, glass bottle, trophy case
    bit 31  n=3    torch, pair of candles, brass lantern

That is TAKEBIT, CONTBIT, ONBIT, TRANSBIT and LIGHTBIT in order, and you can read them off without knowing anything about the game. Write the bit numbers into ATTR, delete the _confirm block the tool left in the file, and the map is complete.

Tested against one game

Calibration has been verified against Zork I, because that is the only story file with an independently known-correct map. The techniques it uses are ZIL library conventions rather than Zork facts, so it should hold across Infocom v3 titles, but treat a first run on a new game as something to check rather than trust. Version 3 only.

What can be proved about a port

Less than for a world you wrote, and the badge says so rather than pretending otherwise.

TierPath AWhy
T0 schemaRunsThe manifest is just data
T1 integrityRunsStory header, room map keys and assets are checkable
T2 graphNot runA compiled binary's dependency graph cannot be read, only explored
T3 replayNot runDepends on T2 having passed
T4 designNot runDepends on a readable world

So a Path A game reaches valid and not playable. Every validate run prints which tiers it actually performed and which it skipped, because a badge implying more verification than was done is the one thing that would discredit certification entirely.

Recovering a graph by exploration is real work rather than a shortcut, and it is staged rather than faked. Until it exists, a port carries a walkthrough that a human wrote and nothing mechanical vouches for it.

Rights, and where story files come from

Folio ships no game data. There is no story file in this repository and there never will be. That is the same posture ScummVM has held for twenty years and the reason it survived a legal challenge that a less careful project would not have.

You supply the story file, and you are responsible for having the right to. The manifest's license field is where you declare it. A game whose licence is "unknown" is playable locally but the gallery will not host it, and validation warns with W105 rather than failing, because an undeclared licence is a distribution problem and not a broken game.

Note that a permissive source licence is not permission to use a name. Some classic games have had their source released while their titles remain live trademarks, so the safe framing for a port is what the game is rather than what it is called.

Path A tests in this repository skip loudly when no story file is supplied rather than failing, and print how to point them at one. A suite that silently reports success while testing half of what it claims is worse than one that fails, because nobody investigates a green run.
