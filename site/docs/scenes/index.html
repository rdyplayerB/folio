Making games

Scenes and verbs

Everything in the two previous pages was logic. This is the layer that draws. It is the one part of Folio that is real code rather than data, and it is the only part a maker owns pixel by pixel.

What the engine draws without you

Almost all of it. The engine ships the board, and a game supplies the picture in one pane. That division is deliberate: uniform furniture is what lets wildly different games sit on one shelf without the shelf falling apart.

You do not lay out the compass, the verb grid, the text pane, the inventory strip, the status bar, the save slots or the on-screen keyboard. You cannot move them either. What you write is the contents of the scene pane, the sixteen-pixel icons in the inventory strip, and the verb map that turns a click into a command.

Nothing generates scene art

There is no art pipeline. A Path B world with no presentation code renders every room as the placeholder above, and it stays that way until somebody writes a draw function for each room. That is the largest piece of manual work in making a Folio game look finished, and automating it is open work.

The state object

Everything the presentation layer reads arrives as one plain object, the World State Contract. It is identical whether the game underneath is a 1988 binary or a world you wrote last week, which is why the same drawing code works for both. 

{
  roomId:    "LIVING-ROOM",     // which scene to draw
  roomName:  "The Living Room",
  score: 35, moves: 13,
  dark:      false,               // engine draws the dark itself
  objects:   ["LAMP","SWORD","RUG"],  // visible here, incl. open containers
  inventory: ["LAMP"],
  contents:  { SACK: ["GARLIC"] }, // one level into open containers
  flags:     { LAMP: { ONBIT: true } },
  exits:     { NORTH: "KITCHEN", EAST: false },
  globals:   { … },
  fighting:  false,               // a hostile actor is present
  lampTurns: 27                   // or null when the game has no lamp
}

Read it, never write to it. On Path A it is a projection of live interpreter memory, and writing would mean the picture and the game disagreed.

Drawing a room

Scenes attach to GUE.scenes, keyed by the same room ids the logic uses. A scene is an object with a draw function and usually a hotspots function. 

GUE.scenes = GUE.scenes || {};

GUE.scenes['PORCH'] = {
  // ctx   a 2D canvas context, already translated and clipped to the pane
  // S     the state object above
  // t     a frame counter, for anything that moves
  draw: function (ctx, S, t) {
    ctx.fillStyle = '#5c94fc';  ctx.fillRect(0, 0, 144, 62);   // sky
    ctx.fillStyle = '#00a800';  ctx.fillRect(0, 62, 144, 42);  // grass
    ctx.fillStyle = '#d8d8d8';  ctx.fillRect(44, 30, 56, 44);  // house
    if (S.flags.CELLAR_DOOR && S.flags.CELLAR_DOOR.OPENBIT) {
      ctx.fillStyle = '#000000'; ctx.fillRect(20, 80, 22, 14);
    }
  },
  hotspots: function (S) {
    return [
      { x: 44, y: 30, w: 56, h: 44, obj: 'HOUSE' },
      { x: 20, y: 80, w: 22, h: 14, obj: 'CELLAR-DOOR' },
      { x:  0, y: 44, w: 20, h: 30, dir: 'NORTH' }
    ];
  }
};
the canvas
144 × 104 Always. Draw in those coordinates and never scale for the device. On a phone the engine scales the whole pane by an integer factor so the picture doubles without going soft, and your code never learns it happened.
darkness
When S.dark is true the engine draws the dark and never calls your draw. You do not handle it.
errors
A draw that throws is caught, warned about once, and replaced with the placeholder. One broken room will not take the game down.
missing scenes
A room with no entry in GUE.scenes gets the placeholder and a console warning naming the room, which is the fastest way to find what you have not drawn.

Hotspots

A picture full of things is only playable if the player can tell which things. hotspots returns rectangles in the same 144 × 104 space, recomputed every frame from state, so a hotspot can appear and disappear with the world.

{x, y, w, h, obj}
A thing. obj is the id the logic knows it by.
{x, y, w, h, dir}
A way out. go and exit work as aliases, and an obj named like _go_north is also read as a direction.
Overlap is resolved by size, not by order

Room-filling scenery is normally declared around the props sitting on it, so when rectangles overlap the smallest wins. That is what makes clicking a mailbox in front of a house select the mailbox. Later declaration breaks ties, so a prop still beats same-sized scenery.

Objects and exits are ranked separately. While a verb other than LOOK is armed, an object always beats an exit underneath it, because arming a verb is a statement about a thing. With nothing armed, a bare click on a doorway walks it.

On a touch screen the engine widens every hit test and, if a tap still misses everything, reaches for the nearest hotspot within a thumb's width rather than swallowing the tap. You do not need to make targets finger-sized yourself.

Inventory sprites

The inventory strip draws each carried item as a 16 × 16 icon. Supply one function that draws any of them. 

GUE.sprites = {
  draw: function (ctx, id, x, y, t) {
    if (id === 'LANTERN') { /* …draw at x, y in a 16×16 box… */ return; }
    throw new Error('no sprite');   // falls back to a lettered box
  }
};

Throwing is a legitimate answer. The engine catches it and draws the item's first letter in a box, so a game with no sprites is still playable and readable.

The verb map

The verb map turns a click into a command string. Path B generates one automatically, because verbs and nouns there are already the ids the rules match on. Path A needs one written, because a Z-machine parser has idioms and its object ids are not words a player would type. 

GUE.verbmap = {
  // what to show the player when they point at something
  noun: function (objId) { return NAMES[objId] || objId.toLowerCase(); },

  // the line actually submitted to the game
  command: function (verb, objId, obj2Id, S) {
    if (verb === 'USE' && objId === 'KEY') return 'unlock door with key';
    return verb.toLowerCase() + ' ' + this.noun(objId);
  },

  // does this verb need a second object before it can be sent?
  needsSecond: function (verb) { return /^(USE|HIT|GIVE)$/.test(verb); },

  // words no player would guess, offered as buttons on the keyboard
  magicWords: ['xyzzy', 'plugh']
};

Returning null from command means the click is refused, which is how you stop a verb being sent for something it cannot apply to. USE and HIT are two-object verbs on the board, so the engine will ask for a second target before calling you.

Sound

Optional, and entirely yours. The engine calls it and survives its absence.

init()
Called on the player's first gesture, which is when a browser will allow audio to start.
update(S)
Called as state changes, so music can follow the room or react to S.fighting.
sfx(name)
Called for one-off events.
muted
A boolean the engine's own menu toggles. Volume lives in the game's menu, not in browser chrome.

Drawing in the house style

These rules were not chosen from taste. They came out of putting candidate art beside real 1988 screenshots and asking fresh critics which was genuine, then reading back the tells they named.

  • Block colour with dark outline shading, not heavy dithering. This one was wrong in three earlier drafts. Dense dithering is an EGA and Amiga signature; console art of this era blocks colour in and shades with outline.
  • Neighbouring tiles should fight. Coherent, harmonious palettes read as modern. The hardware forced clashes and the clashes are the look.
  • One pixel grid per scene. Mixing effective resolutions inside one picture is the fastest way to look fake.
  • Every scene should be a moment of play rather than a landscape. Something in it should be worth clicking.
  • No global filters. No scanline overlay, no bloom, no CRT curve on the art itself.

The engine's own furniture stays uniform on purpose while the games clash wildly. That contrast is the point: coherence lives in the chrome so divergence can live in the pictures.
