Getting started

Your first game

From an empty directory to a playable, validated .folio. Everything here is plain JSON in your own text editor, because that is the whole toolchain today. About ten minutes.

Install

npm i -g folio-engine
folio            # prints the six commands

You can also run it out of a clone with node packages/cli/folio.js, which is what the examples in this manual were checked against.

One room

A game is a directory. Two files are mandatory and everything else is optional, so start with the smallest thing that can exist. 

porch/
├── manifest.json
├── walkthrough.folioscript
└── logic/
    └── world.json

manifest.json

Seven fields are mandatory. The validator will tell you if you miss one, and the manifest reference explains each. 

{
  "id": "porch",
  "title": "Porch",
  "author": "You",
  "folioVersion": "0.1.0",
  "logicType": "world",
  "license": "MIT",
  "contentRating": "all-ages"
}

logic/world.json

This is the game. meta.start names the room the player wakes up in, and it has to be a real room id or nothing will boot. 

{
  "meta": { "title": "Porch", "start": "PORCH" },
  "rooms": [
    {
      "id": "PORCH",
      "name": "The Porch",
      "prose": "Paint curls off the boards. A cellar door lies flat against the ground.",
      "exits": []
    }
  ],
  "items": [],
  "rules": []
}

walkthrough.folioscript

One command for now. This file is the proof the game can be finished.

look

Pack it, and get told off

folio pack porch/ porch.folio
packed porch.folio  947 bytes

folio validate porch.folio
WARNING W106  no aiDisclosure block
ERROR   E310  the win state is not reachable
        No sequence of reachable actions fires a "win" effect. Either a puzzle
        has no solution from the start state, or nothing declares a win.

INVALID  porch.folio  1 error
  ran T0, T1, T2. Not checked: T3, T4

That is the point of the thing, arriving in the first thirty seconds. A world with no ending is not a game, so the validator refuses it before you have written a second room. It also stops after T2 rather than pretending it checked more.

It will still play, though. Validation gates the badge, not the engine.

folio play porch.folio

Porch

The Porch
Paint curls off the boards. A cellar door lies flat against the ground.

PORCH  0/0 >

The prompt shows the room id, the score and the move count. Everything you type goes to the same place the verb buttons send in the browser, so the terminal is a real play session and not a debug mode.

A second room, and something to pick up

Exits are declared per room and are one way. If you want to walk back, say so. Items live in a room by id, and TAKEBIT is what makes one portable. 

  "rooms": [
    {
      "id": "PORCH",
      "name": "The Porch",
      "prose": "Paint curls off the boards. A cellar door lies flat against the ground.",
      "exits": [{ "dir": "NORTH", "to": "HALL" }]
    },
    {
      "id": "HALL",
      "name": "The Hall",
      "prose": "A narrow hall. A side table holds something.",
      "exits": [{ "dir": "SOUTH", "to": "PORCH" }]
    }
  ],
  "items": [
    {
      "id": "KEY",
      "name": "iron key",
      "location": "HALL",
      "roomProse": "An iron key lies on the side table.",
      "attributes": { "TAKEBIT": true }
    }
  ],

name is what the player is shown. roomProse is the line that appears in the room description while the item is still lying there, and it stops appearing once the item moves. Writing both is what makes a room read like prose rather than like an inventory listing.

Rules, and an ending

A rule is the only place a Folio world does anything interesting. It matches a command, optionally tests some conditions, and then applies effects. Everything you do not write a rule for falls through to the engine's built-in behaviour. 

  "rules": [
    {
      "on": { "verb": "TAKE", "noun": "KEY" },
      "if": [{ "type": "in-room", "item": "KEY" }],
      "do": [
        { "type": "take", "item": "KEY" },
        { "type": "score", "value": 10 },
        { "type": "print", "text": "The key is colder than the room." },
        { "type": "win", "text": "*** You have won ***" }
      ]
    }
  ]

Update the walkthrough to match, because it now has to reach that ending. 

# north, then take the key
north
take key
folio validate porch.folio

PLAYABLE  porch.folio  T0+T1+T2+T3+T4 passed with 6 warnings
  completed in 2 moves for 10 points, 100% of rooms visited
  ran T0, T1, T2, T3, T4

That is a complete game. It is a bad one, and the six warnings say so, but the engine will run it and the validator will vouch that it can be finished.

A locked door

Gating is the one pattern worth learning properly, because almost every puzzle is a variation on it. An exit carries a condition, a rule sets the flag that satisfies it, and the flag is the only thing connecting them. 

// at the top level, next to "rooms"
"flags": { "doorUnlocked": false },
// on the PORCH room
"exits": [
  { "dir": "NORTH", "to": "HALL" },
  { "dir": "DOWN", "to": "CELLAR",
    "condition": { "type": "flag", "flag": "doorUnlocked" } }
]
// two rules, and the order matters
{
  "on": { "verb": "UNLOCK", "noun": "CELLAR-DOOR" },
  "if": [{ "type": "carrying", "item": "KEY" }],
  "do": [
    { "type": "set-flag", "flag": "doorUnlocked", "value": true },
    { "type": "print", "text": "The key turns with a sound like a cough." },
    { "type": "score", "value": 5 }
  ]
},
{
  "on": { "verb": "UNLOCK", "noun": "CELLAR-DOOR" },
  "do": [{ "type": "print", "text": "It is locked, and you have nothing to turn." }]
}
The first matching rule wins

Rules are tried in array order and the first one whose trigger and conditions all pass is the only one that runs. So the specific case goes first and the general one goes last, exactly like the two rules above. Put them the other way round and the door never unlocks, which is the most common bug in a hand-written world.

That second rule is also what stops the game feeling like a form. Without it, trying to unlock the door without the key falls through to "Nothing happens.", and the player learns nothing. The failure branch is where the writing goes.

Darkness and a lamp

Mark a room dark and it stays unreadable until a lit light source is in it or carried. That is engine behaviour, so all you supply is the lamp. 

// the room
{ "id": "CELLAR", "name": "The Cellar", "dark": true,
  "prose": "Earth floor, stone walls, and a smell like old coins.",
  "exits": [{ "dir": "UP", "to": "PORCH" }] }

// the lamp: LIGHTSOURCE makes it count, fuel makes it run out
{ "id": "LANTERN", "name": "lantern", "location": "HALL",
  "attributes": { "TAKEBIT": true, "LIGHTSOURCE": true },
  "fuel": 40 }

// lighting it is a rule, because the engine has no opinion about how
{ "on": { "verb": "LIGHT", "noun": "LANTERN" },
  "if": [{ "type": "carrying", "item": "LANTERN" }],
  "do": [
    { "type": "light", "item": "LANTERN" },
    { "type": "print", "text": "The lantern catches, and the dark backs off a step." }
  ] }

// and a timer burns the fuel down, which drives the gauge in the status bar
"timers": [
  { "startFlag": "_lit_LANTERN", "fuelFor": "LANTERN", "turns": 40,
    "do": [
      { "type": "extinguish", "item": "LANTERN" },
      { "type": "print", "text": "The lantern gutters once and goes out." }
    ] }
]

_lit_LANTERN is an engine-managed flag rather than one you declare. Lighting an item sets it, and you can test it like any other flag, which is how you write the branch where the player gropes around in the dark and finds nothing. The internal flags are listed in the reference.

The walkthrough is a test

One command per line, # starts a comment, and blank lines are ignored. It runs from a cold start with no state injected and no privileged verbs, so it is exactly what a player could type. 

# Porch — cold start, no state injection
north
take key
take lantern
south
unlock cellar-door
light lantern
down
take locket

You can also pin the shape of the run, so a walkthrough that still finishes by accident gets caught: 

north
expect: room HALL
take key
expect: score 10

Three assertions exist: expect: room ID, expect: score N and expect: moves N. A failure reports like this: 

ERROR  E403  line 2: expected score 99, got 0
A rough edge worth knowing

That line number counts commands, not lines in the file. Comments and blank lines are stripped before anything is numbered, so an assertion sitting on file line 5 can be reported as line 2. Count from the top ignoring comments and you will find it.

Reading the design review

Finish the game and the validator stops reporting errors and starts reporting opinions. This is the real thing, from the worked example that ships in the repo: 

folio validate cellar-door.folio

WARNING W500  only 3 rooms
        Short enough to read as a demo. Zork I runs 82 rooms; a short story
        need not, but a novel should not come out this size.
WARNING W504  the map runs 0 loops per room (a tree)
        Corridor maps are the signature of generated geography. Zork runs 0.67
        loops per room, which is what lets a player take a shortcut and feel
        the map as a place rather than a menu.

PLAYABLE  cellar-door.folio  T0+T1+T2+T3+T4 passed with 2 warnings
  completed in 8 moves for 15 points, 100% of rooms visited
  "playable" means a path exists, not that a human can find it.

Those thresholds are measured rather than invented. They come from replaying Zork I and recording what it actually does, and you can point the same measurement at your own game with folio profile. If your game is deliberately small or deliberately linear, ship a brief.json saying so and T4 will grade you against your own intent instead. The dials cover that.
