Making games

Writing a world

The complete reference for logic/world.json, the declarative format behind Path B. It is data, never code, which is why a .folio from a stranger is safe to open and why the validator can see everything a game is able to do before running it.

There is a machine-readable version of this page

world-0.1.0.json is the JSON Schema for everything below. Point an editor at it for autocomplete, constrain a model against it to generate only valid structures, or validate without Node. folio validate checks against that same file, so it cannot drift from what the engine accepts.

Deliberately less expressive than Inform

The vocabulary below is closed. Seventeen conditions, sixteen effects, and no way to add another without a spec revision. That bound is the point: because every effect comes from a fixed list, the dependency graph can be computed statically rather than discovered by playing. You give up arbitrary logic and you get provable completability.

The top level

{
  "meta":   { … },   // required
  "flags":  { … },   // optional, your named booleans
  "counters": { … }, // optional, your named integers
  "rooms":  [ … ],   // required
  "items":  [ … ],   // required, may be empty
  "actors": [ … ],   // optional
  "rules":  [ … ],   // optional, but a game with none is a museum
  "timers": [ … ]    // optional
}

flags is a plain object of your own named booleans, and it is the memory of the world. Everything a puzzle needs to remember lives here.

meta

start
string · required The room id the player begins in. If it does not name a real room the game will not boot and validation stops at E300.
title
string Shown above the opening room description.
seed
number Seeds the world's random number generator. Runs are deterministic, which is what makes walkthrough replay and regression transcripts possible. The CLI and validator override this with 1234 so a run is reproducible across machines.
defaults
object Overrides for the engine's built-in responses. See below.
magicWords
string[] Words a player would never guess to type, offered as one-tap buttons on the on-screen keyboard. Read by the presentation layer rather than by the logic.

meta.defaults

The engine answers commands you did not write rules for. These thirteen strings are how you make those answers sound like your game rather than like a parser. Every one is optional and falls back to the text on the right.

KeySpoken whenDefault
blockedWalking a direction with no exitYou cannot go that way.
darkLooking in an unlit dark roomIt is pitch black.
whatTAKE with no nounTake what?
alreadyTaking something already carriedYou already have that.
absentActing on something not hereYou do not see that here.
fixedTaking something without TAKEBITThat is not something you can carry.
takenA successful takeTaken.
nothaveDropping something not carriedYou are not carrying that.
droppedA successful dropDropped.
alreadyOpenOpening something already openIt is already open.
lockedOpening something that will not openIt will not open.
emptyINVENTORY while empty-handedYou are empty-handed.
unknownAny verb with no rule and no built-inNothing happens.

unknown earns the most attention. It is what a player hears every time they try something you did not anticipate, so it is the single line that decides whether your world feels responsive or dead.

rooms

id
string · required Unique. Convention is upper-case with hyphens, matching what the Z-machine path produces.
name
string The heading the player sees. Falls back to the id, which looks like a bug, so write one.
prose
string The room description, printed on entry and on LOOK.
dark
boolean The room is unreadable unless a lit LIGHTSOURCE is carried or present.
region
string Which part of the world this room is in, such as "afghanistan" or "malibu". Rooms in different regions are not next to each other, so a compass exit between them is reported as W512. Optional, and worth setting on anything that spans more than one place.
exits
object[] Ways out. See below.
variants
object[] Alternative descriptions, each { if: [...], prose: "..." }, tried in order. The first whose conditions all hold replaces prose. This is how a room changes once something has happened in it, and without it the only dynamic room text was an item's roomProse.

exits

Exits are declared per room and are one way. A return journey is a second exit on the other room. The validator does not require symmetry, because one-way drops are a real design tool, but it does check that both ends exist.

dir
string · required One of NORTH SOUTH EAST WEST NE NW SE SW UP DOWN IN OUT. Anything else is silently ignored, so check your spelling.
to
string · required Destination room id.
condition
condition The way is blocked until this passes.
door
string An item id. The way is blocked while that item is closed, which is the shorthand for a door you literally open.
hidden
boolean While blocked, the exit vanishes entirely rather than showing as blocked.

Three states, not two

This is the part worth reading twice, because it is what the compass draws.

SituationContract reportsCompass shows
Open wayNORTH: "KITCHEN"Lit and clickable
Blocked, not hiddenDOWN: falseGreyed out, visible
Blocked and hiddenabsentNothing at all
No exit declaredabsentNothing at all

The middle state carries real information: a door you can see and cannot yet open tells the player there is something here to solve. Use hidden only when the passage itself is the secret.

items

id
string · required Unique across items and actors. This is what commands and rules refer to.
name
string What the player is shown, in the inventory and in hover labels.
location
string · required A room id, the literal "PLAYER" to start it carried, another item's id to start it inside a container, or "NOWHERE" to keep it out of play until a rule moves it in.
roomProse
string A line appended to the room description while the item is still lying in that room. It stops appearing the moment the item moves, so a room reads as prose rather than as a list.
attributes
object Booleans the engine understands. See below.
fuel
number Turns of light remaining, for a LIGHTSOURCE. Drives the lamp gauge in the status bar. Burn it down with a timer's fuelFor.

attributes

Five booleans have meaning to the engine. Anything else you add is carried through to the presentation layer untouched and ignored by the logic.

AttributeEffect
TAKEBITThe item can be picked up. Without it, TAKE answers with defaults.fixed.
LIGHTSOURCEThe item counts as light when lit, defeating a dark room.
ONBITThe item starts lit. Usually you leave this off and light it with a rule.
OPENBITThe item starts open. Matters for containers and for exits with a door.
TRANSPARENTYou can see inside without opening it, so its contents are visible from the start.

actors

Actors are things that are somebody rather than something. They are projected into the scene the same way items are, but they cannot be carried and they are what the fighting flag reads from.

id
string · required Unique across items and actors.
name
string What the player is shown.
location
string · required A room id, "NOWHERE" until they arrive, or "PLAYER" to travel with the player. A companion at "PLAYER" is present in every room you enter, so speaking to them works everywhere instead of hitting the absent default. Move someone into or out of the party with move-actor.
description
string What LOOK at them says.
hostile
boolean While a hostile actor shares your room, the contract reports fighting: true, which the presentation layer can use to change the music or the scene. It does not itself do any harm; the harm is a rule or a timer.
attributes
object As for items.

Move them with the move-actor effect.

rules

A rule is a trigger, a guard and a consequence. It is the only place a world does anything the engine did not already know how to do. 

{
  "on": { "verb": "UNLOCK", "noun": "CELLAR-DOOR", "room": "PORCH" },
  "if": [ /* conditions, all must pass */ ],
  "do": [ /* effects, applied in order */ ]
}
on.verb
string Matched case-insensitively. Omit to match any verb.
on.noun
string Matched case-insensitively against the object id. Omit to match any noun, including none.
on.second
string A second object, for pairings like using a key on a door. USE and HIT ask the player for one on the board whenever a rule pairs objects under that verb. A rule without second will never match a two-object command, so write the pairing above the single-object fallback.
on.room
string Only fires while the player is in this room.
if
condition[] Every one must pass. Omit for an unguarded rule.
do
effect[] Applied in order. All print text is joined with newlines and returned as the response.
First match wins, and nothing else runs

Rules are tested in array order. The first whose trigger matches and whose conditions all pass is applied, and the scan stops there. Write the specific case above the general one.

A rule that matches on trigger but fails its conditions does not block later rules, so the usual shape is a guarded rule followed by an unguarded fallback for the same trigger. That fallback is where the writing lives, and a world without them answers "Nothing happens." to everything a player improvises.

conditions

Ten types. Anything unrecognised evaluates to false rather than throwing, so a typo silently disables a rule. W313 catches the common cases.

TypeFieldsTrue when
flagflag, valueThe named flag equals value, which defaults to true
carryingitemThe player is holding it
in-roomitemIt is lying in the current room, not carried
presentitemCarried or in the room, whichever

visitedroomThe player has been there at least once
openitemIt is open, by OPENBIT, TRANSPARENT or an open effect
lititemIt is currently alight
score-at-leastvalueScore is at or above the number
counter-at-leastcounter, valueA counter is at or above the number
counter-equalscounter, valueA counter is exactly the number
actor-hereactorThat actor is in this room

// carrying the key, and the door is not already unlocked
"if": [
  { "type": "carrying", "item": "KEY" },
  { "type": "not",
    "condition": { "type": "flag", "flag": "doorUnlocked" } }
]

effects

Fourteen types. Unknown effects are inert at runtime and rejected by validation, so a typo fails loudly rather than quietly.

TypeFieldsDoes
printtextAdds a line to the response
set-flagflag, valueSets a flag, defaulting to true
takeitemMoves it to the player, ignoring TAKEBIT
move-itemitem, toMoves it to a room id, "PLAYER", or a container id
destroyitemRemoves it from play, by moving it to NOWHERE
openitemMarks it open
closeitemMarks it closed
lightitemLights it
extinguishitemPuts it out
gotoroomMoves the player, marking the room visited
scorevalueAdds to the score. Negative numbers work
set-countercounter, valueSets a counter outright
add-countercounter, valueAdds to a counter. Negative subtracts
move-actoractor, toMoves an actor to a room id or NOWHERE

losetext or pagesEnds the game as a loss

Note that take ignores TAKEBIT on purpose. The attribute governs what a player may pick up unaided; an effect is you deciding, so it always works.

timers

Timers tick once per move, after the command's rule has run. They are how anything happens that the player did not directly cause. 

{
  "startFlag": "_lit_LANTERN",   // waits until this flag is true
  "fuelFor":   "LANTERN",        // reports elapsed as this item's fuel used
  "turns":     40,               // fires after this many ticks
  "repeat":    false,            // fire once, or every `turns` moves
  "do": [ /* effects */ ]
}
turns
number · required Ticks before firing.
startFlag
string The timer does not tick at all until this flag is true. Without it, it starts counting from move one.
repeat
boolean Fire every turns moves instead of once.
fuelFor
string An item id. Elapsed ticks are published as that item's fuel consumption, which is what moves the lamp gauge.
do
effect[] Applied when it fires. Printed text is appended to that move's response after a blank line.

Built-in verbs, and the four that are not

The engine answers six things by itself. Everything else in the game is yours.

VerbBuilt-in behaviour
The twelve directionsMove if the exit is open, otherwise defaults.blocked
LOOKRe-describe the room, or defaults.dark
TAKEPick it up if it is here and has TAKEBIT
DROPPut down something carried
OPENReports open or refuses. It cannot actually open anything on its own
INVENTORYList what is carried
WAITLet a turn pass, worded by defaults.wait
Half the verb grid does nothing by default

The player is shown eight verbs: LOOK TAKE DROP OPEN CLOSE USE HIT SPEAK. Four of them, CLOSE, USE, HIT and SPEAK, have no built-in behaviour at all in a Path B world. Without rules they answer defaults.unknown, which reads to a player as a broken button.

OPEN is a near miss in the same way. It will tell you something is already open, and otherwise refuse, but only a rule with an open effect can make it succeed. Assume every verb needs writing.

Internal flags

The engine keeps some state in the same flag namespace you write to, using an underscore prefix. You can read these in conditions, which is frequently the clearest way to express something. Do not write to them directly; use the effect.

_open_<ITEM>
Set by open and close. Overrides OPENBIT.
_lit_<ITEM>
Set by light and extinguish. Overrides ONBIT.
_fuelUsed_<ITEM>
Maintained by a timer's fuelFor. Subtracted from fuel to give the gauge.
// "you grope in the dark" — the branch that runs when the lamp is not lit
"if": [
  { "type": "in-room", "item": "LOCKET" },
  { "type": "not", "condition": {
      "type": "flag", "flag": "_lit_LANTERN", "value": true } }
]

Containers

Put an item's location to another item's id and it is inside it. The contract projects container contents one level deep, and only when the container is open or TRANSPARENT. A box inside a box is legal data but the inner contents will not be listed. 

{ "id": "CHEST", "location": "ATTIC",
  "attributes": { "OPENBIT": false } },
{ "id": "COIN",  "location": "CHEST",
  "attributes": { "TAKEBIT": true } }

The coin is invisible until a rule opens the chest. This is the cheapest way to hide something in plain sight, and it costs you no flags.

The patterns worth stealing

A gate

A flag, an exit condition, and a rule that sets it. Every locked door, raised drawbridge and placated guardian is this shape.

A guarded action with a failure branch

Two rules on the same trigger, the guarded one first. The second is not optional polish. It is the difference between a world that answers and one that shrugs.

A hazard that is fair

A repeating timer that prints a warning, and a second timer or a rule that applies lose. Foreshadowing a death is what separates a hazard from an ambush, and T4 measures whether you did it.

A scene change

An exit on the compass claims two places are next to each other. When the story jumps instead — a flight, a flashback, a cut to somewhere else — write it as an action with a goto, so the player does something and the story moves. That is what a cut is. 

{ "on": { "verb": "USE", "noun": "JET" },
  "do": [ { "type": "print", "text": "Fourteen hours, and the light is wrong." },
          { "type": "goto", "room": "BAGRAM" } ] }

An adaptation of a film wired every one of its cuts as a compass exit, because that was the only way anything could move between rooms, and twenty-nine of its thirty rooms ended up joined to somewhere on another continent. Walking out of a Humvee on an Afghan road put the player on the floor of a Las Vegas casino. Declaring region is what lets the validator find those for you.

Counting

A counter and counter-equals, not a chain of near-identical rules. Three visits to the same room reading trip number out of flag state works and is the thing an author reaches for when there are no numbers; there are numbers now.

An ending with pacing

pages instead of text on a win or lose, so the last thing a player reads arrives in beats rather than as one wall. A novel-length adaptation's whole epilogue was a single string, and it read well and was a scroll rather than a scene.

A fight

chance against the world's seeded generator. Rolls differ within a run and repeat exactly across runs, which is what keeps a walkthrough that passed passing. Never gate the only route to the ending on one.

A consumable

destroy the item as part of the effect that spends it. The dependency graph understands that the item is gone, so a puzzle needing it later will be reported as unreachable rather than discovered by a player at move 200.

Check your work continuously

folio validate is fast enough to run on every save. T2 computes the dependency graph from the world rather than trusting your walkthrough, so it finds the dead end you created three rules ago, not the one you happened to walk into.
